### Harness: roma

**Overview**: ROMA is a recursive decomposition harness for tasks with multiple semi-independent goals. An atomizer LLM call first classifies the task as atomic or complex; atomic tasks run a flat ReAct tool-calling loop, while complex tasks are decomposed by a planner into subtasks with a dependency DAG, executed in topological layers (independent subtasks in parallel), and finally synthesized by a dedicated aggregator LLM call. Each subtask recurses through the same atomize/plan/execute pipeline in an isolated memory, with structured results flowing between subtasks via an artifact store. Best suited to tasks whose sub-questions require gathering different information from different sources.

**Component implementations**:
- **memory.py — `ROMAMemory`**: Full-history memory with no compression, summarization, or eviction: every step, plan, and summary record is appended to an ordered list, and context rendering simply concatenates system prompt + task messages + all step messages. Its distinctive addition is an `ArtifactStore` — dicts keyed by subtask index holding each subtask's goal and result text — which formats dependency-specific context for downstream subtasks and all results for the aggregator, plus a generic key-value artifact slot. Each subtask gets its own fresh memory instance, so transcripts never mix across the tree.
- **planning.py — `ROMAPlanning`**: Initial planning makes up to two LLM calls: an atomizer returning a JSON atomic/complex verdict (defaulting to atomic on any parse failure), then, only if complex, a planner returning subtasks (goal + index) and a string-keyed dependency map. Dependencies are validated (unknown indices and self-references dropped); an empty decomposition falls back to atomic. Since the plan state has no metadata field, the decomposition JSON is smuggled through the plan-reasoning string for the action layer to parse; replanning is disabled entirely.
- **action.py — `ROMAAction`**: The recursive driver reads the plan metadata: at depth >= 3 it forces atomic execution; atomic tasks run a ReAct loop that per step rebuilds context, appends a step prompt with tool schemas, calls the LLM, JSON-repairs a think/tools response, executes tool calls sequentially, and treats a `final_answer` call as termination — model errors are logged as error steps and the loop continues, and hitting max steps triggers a forced final-answer LLM call over the full memory. Decomposed tasks compute topological layers (a detected cycle forces all remaining subtasks into one layer), give each subtask a step budget of parent max steps divided by subtask count with a floor of 5, run multi-task layers via a thread pool capped at 2 concurrent workers, inject dependency results into each subtask prompt, recurse at depth+1, and store results in the artifact store. Aggregation is one LLM call over all subtask results parsed for a JSON answer, falling back to concatenated raw results on failure.
- **tool_policy.py — `AllToolsPolicy`**: An all-tools policy: the full tool catalog is formatted into JSON schemas once at initialization (coercing "any" parameter types to string and marking non-nullable parameters required) and returned unchanged at every step with no filtering. It can optionally load a skill registry and expose a skills prompt. `final_answer` gets no special policy treatment; termination is handled in the action layer.
- **prompt.yaml**: Defines a system prompt (used for subtask contexts) mandating the JSON think/tools output protocol, listing tools and optional skills, and rules such as no repeated identical calls and matching answer language to the task. Under planning it defines the atomizer prompt (prefer ATOMIC unless clearly multiple independent parts), the planner prompt (2-4 subtasks, last one typically depending on all others, JSON subtasks + dependencies), and the aggregator prompt (combine results, note contradictions, JSON answer) — the first two consumed by planning, the aggregator by action. The step pre-message re-presents tool schemas, the task, and the output format each turn and demands at least one tool call; the final-answer pre/post messages drive the forced-answer path when max steps are exhausted.
