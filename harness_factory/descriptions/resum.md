### Harness: resum

**Overview**: ReSum is a linear ReAct harness whose distinguishing mechanism is ReSum-style token-budget summarization memory. The flow is: generate a sequential numbered plan at step 0, then run an Action/Observation loop where each step emits a JSON object of think plus multi-tool calls, with a plan-progress review every 8 steps. When the working context nears its token budget, the entire history is compressed by an LLM summarization call and the context is hard-reset to just the system prompt plus a summary observation, so the run restarts from compressed state rather than dragging raw history forward. It terminates on a `final_answer` tool call or a forced answer at the max-step limit, and fits long-horizon sequential tasks where context growth, not branching decomposition, is the bottleneck.

**Component implementations**:
- **memory.py — `ReSumMemory`**: Maintains two parallel states: a working message list initialized as [system prompt, user task], and a never-reset full trajectory of steps/plans/summaries for logging. Each step, plan, and summary is appended to both; context is rendered by returning the working messages verbatim with summary-count/token-count metadata. Summarization fires when the working context reaches 90% of a 31768-token budget (primary) or every 4 rounds (fallback). It stringifies everything after the first two messages, picks a first-summary prompt or an iterative prompt that includes the previous summary, calls the main LLM as a single user message, strips think blocks, extracts and re-wraps summary tags, then rebuilds the working context as [system prompt, synthetic user observation containing the question and the summary]; empty or failed summaries leave the context untouched.
- **planning.py — `LinearPlanning`**: At step 0 it prompts the LLM (with tool schemas truncated to 2000 characters) to produce a 3-7 step ordered numbered roadmap, stored as plain text and appended into memory. Replanning triggers every 8 steps: it sends a progress-analysis prompt over the current memory view (system message dropped) and appends the resulting summary state to memory. The current plan text is exposed as the directive.
- **action.py — `ReActAction`**: Owns the main loop: plan at step 0, then while no final answer and within max steps, check replan, build memory view and tool selection, render a Jinja step prompt appended as a user message, and call the LLM; model-call failures are recorded as error steps and the loop continues. Responses are parsed with json_repair into think plus a tools list; each call executes sequentially, tool errors become error-text observations, and a `final_answer` call short-circuits with its answer. If max steps are hit without an answer, one extra LLM call over memory with dedicated pre/post prompts forces a final answer (parsed for a JSON answer field) and is recorded as a trajectory step. A no-op response-processing hook exists for subclasses.
- **tool_policy.py — `AllToolsPolicy`**: An all-tools policy with no filtering: the full catalog is exposed at every step as pretty-printed JSON schemas (untyped params coerced to string, non-nullable params marked required). An optional skills registry is loaded only when explicitly enabled and rendered as prompt text for system-prompt injection. `final_answer` is not special-cased here; it is handled by the action loop.
- **prompt.yaml**: Defines `system_prompt` (linear roadmap-following rules, per-step JSON think/tools output format, tool minimalism, no duplicate calls; rendered with tools and optional skills), `planning.initial_plan` (3-7 numbered steps, verification near the end; used by planning), `summary.update_messages` (progress review at step N; used by replanning), `memory.query_summary_prompt` and `query_summary_prompt_last` (ReSum extraction of only certain, explicitly stated information into summary tags, the latter building on the previous summary; used by memory), `step.pre_messages` (per-step action prompt with tool list and task, at least 1 and up to 5 tool calls, answer language matching the task; used by action), and `final_answer.pre_messages`/`post_messages` (forced-answer JSON think/answer format; used by action's forced finish).
