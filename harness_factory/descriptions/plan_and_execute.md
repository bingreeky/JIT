### Harness: plan_and_execute

**Overview**: Plan-and-Execute is a linear ReAct harness: at step 0 it generates an ordered numbered roadmap (3-7 steps), then runs an action/observation loop where each iteration the LLM emits a JSON object containing a "think" field and a list of tool calls (up to 5 per step). Every 8 steps it inserts a progress-summary turn that re-analyzes execution against the roadmap. The full trajectory — plan, steps, summaries — is kept uncompressed in memory and replayed as context. It fits tasks that benefit from a clear sequential roadmap with linear dependencies rather than branching/graph decomposition, and short runs (roughly under 15 steps) where context length is not a concern.

**Component implementations**:
- **memory.py — `FullHistoryMemory`**: A full-history memory with no compression, summarization, or eviction. It stores the system prompt, the task, and a single ordered list holding step records, plan states, and summary states interleaved in arrival order; `update`, `update_plan`, and `update_summary` all just append. Context is rendered by concatenating the system message, the task messages, and every stored item's messages in order, so the LLM always sees the entire trajectory. A helper filters the list to return only step records.
- **planning.py — `LinearPlanning`**: On the first call it strips the system message from the memory view, appends the initial-plan prompt formatted with the task and the tool schemas truncated to 2000 characters, and calls the LLM once; the raw response text (plus any reasoning content) becomes the plan state and the current directive. `should_replan` fires whenever the step number is a positive multiple of the summary interval (default 8); the update path appends the summary prompt with the current step number and returns the LLM's analysis as a summary state, which memory appends rather than replacing the plan.
- **action.py — `ReActAction`**: Owns the main loop. Step 0 builds context, selects tools, produces the plan, and logs it; then, while no final answer exists and the step number is at most `ctx.max_steps`, it checks the replan trigger (a summary consumes a step number), renders the per-step prompt via Jinja with the tool-schema JSON and task, appends it to the full memory view, and calls the LLM. The response is parsed with json_repair into a think string and a tools list (handling dict, list-of-dicts, and single-dict shapes); each call is dispatched via the runtime's tool executor, with tool errors captured as error-observation strings and model-call failures recorded as error steps that still advance the counter. A `final_answer` tool call terminates the loop; if max steps are exhausted, a forced-final-answer path replays memory with pre/post prompts asking for a JSON think/answer object, recording that call as an extra trajectory step. Token counts, durations, and a subclass hook for intercepting raw responses are also tracked.
- **tool_policy.py — `AllToolsPolicy`**: An all-tools policy — every step exposes the entire tool catalog with no filtering; schemas are serialized once at initialization into a JSON list of name/description/parameters, treating non-nullable inputs as required and coercing "any" types to string. It optionally loads a skills registry (when explicitly enabled) and returns its formatted text for prompt injection alongside the tools. There is no per-tool constraint logic; `final_answer` is handled by the action loop, not here.
- **prompt.yaml**: Defines `system_prompt` (linear execution policy, JSON think/tools output format, tool and optional skills listing, no-repeat and language-matching rules; rendered by the kernel into memory's system message), `planning.initial_plan` (produce a 3-7 step numbered roadmap with linear dependencies and a verification step near the end; consumed by planning's init), `summary.update_messages` (at step N, analyze which goals are done and what to do next; consumed by planning's update), `step.pre_messages` (per-step instruction with tool list, task, an example JSON output, and the "up to 5 tools, at least one, do not repeat" constraints; consumed by action each iteration), and `final_answer.pre_messages`/`post_messages` (fallback prompts that frame the memory dump and demand a JSON think/answer reply; consumed by the forced-answer path).
