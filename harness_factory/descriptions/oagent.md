### Harness: oagent

**Overview**: OAgent is a multi-path ensemble harness that solves one task by running several independent expert agents sequentially and then having an LLM critic pick or synthesize the best final answer. By default it runs 1 Plan-and-Execute worker followed by 2 ReAct workers, splitting the outer step budget evenly (max_steps // num_experts, minimum 5 steps each). Each expert runs a full inner ReAct loop with its own fresh full-history memory and a snapshotted/reset filesystem workspace, so paths cannot contaminate each other; results only merge at the final voting stage. This heterogeneous redundancy suits tasks where a single trajectory may stall or miss evidence, at the cost of multiplied compute.

**Component implementations**:
- **memory.py — `OAgentMemory`**: The outer coordinator memory stores only the system prompt and task (no per-step history) and renders a minimal system+task context; plan/summary updates are no-ops; it accepts the merged trajectory written back after all experts finish. A separate `FullHistoryMemory` class, instantiated fresh per expert inside the action module, appends every step/plan/summary and renders the entire uncompressed history — no summarization or eviction at all.
- **planning.py — `NoPlanning`**: NoPlanning — the initial "plan" is a fixed one-line placeholder, replanning is always disabled, and the directive is simply the task text echoed back. Each expert gets its own NoPlanning instance; planning does not interact with memory beyond that placeholder.
- **action.py — `OAgentAction`**: `run` snapshots the workspace baseline, then for each expert resets the workspace, builds a system prompt combining the base prompt with a PE- or ReAct-specific prompt, and runs an inner ReAct loop: render the step prompt (tool schemas + task), call the LLM, parse the JSON reply via json_repair into a think string plus tool-call list, execute calls sequentially with errors returned as observations, stop on final_answer. Model-call failures are logged as error steps and the loop continues; hitting the per-expert step cap triggers a forced final-answer call over the full memory. Each expert's output directory is archived as output{i}; after the critic vote (evidence capped at 5 observations of 500 chars each per expert, JSON verdict with selected_expert + answer, fallback to expert 1 on parse failure) the winner's output is restored, trajectories are merged with expert-name tags, and per-expert answers (truncated to 1000 chars) go into metadata.
- **tool_policy.py — `AllToolsPolicy`**: AllToolsPolicy — exposes the entire tool catalog at every step with no filtering, pre-serializing JSON schemas (coercing "any" types to string, non-nullable params required). Optionally loads a skills registry for prompt injection when enabled; final_answer is handled in the action parser, not here.
- **prompt.yaml**: `system_prompt` (all experts) mandates the JSON think/tools action format with worked examples, verification and minimal-tool-use rules; `action.pe_worker_system_prompt` and `action.react_worker_system_prompt` differentiate expert styles (methodical roadmap vs. adaptive explore); `action.critic_prompt` scores answers on compliance, evidence, logic, specificity and returns a JSON verdict; `step.pre_messages` is the per-step user prompt (tool list, up to 5 tool calls, at least 1, answer language must match the task); `final_answer.pre/post_messages` drive the forced-answer fallback; `planning.initial_plan` and `summary.update_messages` are static placeholders.
