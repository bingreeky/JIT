### Harness: flash_searcher

**Overview**: Flash-Searcher is a DAG-planned ReAct harness: an upfront planning LLM call decomposes the task into 1-5 relatively independent goals, each with 1-5 candidate execution paths (approach plus success criteria), then a ReAct action/observation loop advances unresolved goals in parallel while treating paths within a goal as sequential fallbacks. Every 8 steps a summary call analyzes goal/path completion status and prescribes the next parallel sub-paths, which replaces the working directive. The agent may issue up to 5 tool calls per step across independent goals, and terminates via a `final_answer` tool call or a forced answer at the step limit. It fits multi-goal tasks that benefit from parallel decomposition and fallback strategies.

**Component implementations**:
- **memory.py — `FullHistoryMemory`**: A full-history memory with no compression, summarization, or eviction — intended for short tasks (under ~15 steps). It stores the system prompt, the task, and a single ordered list interleaving step records, plan states, and summary states; each appended step carries the model I/O, tool calls, observations, and timing. Context is rendered by concatenating the system message, task messages, and every stored item's messages verbatim, in order.
- **planning.py — `FlashDAGPlanning`**: At step 0, an LLM call with the planning prompt (task plus tool schemas truncated to 2,000 characters) produces the goal/path DAG as free-form markdown text, stored both in memory and as the current directive. Replanning triggers whenever the step number is a positive multiple of the summary interval (default 8): two summary prompts are appended to the full history and the LLM's status analysis becomes the new directive, appended to memory as a summary record. The directive is simply the latest plan or summary text.
- **action.py — `ReActAction`**: Owns the main loop: after initial planning, each iteration optionally replans, rebuilds full context, appends a per-step prompt (tool list plus task), and calls the LLM expecting JSON with a "think" field and a "tools" array, parsed leniently via json_repair (lists and single dicts are normalized). Tool calls execute sequentially; execution errors become error observations, and model-call failures are recorded as error steps without halting. Encountering `final_answer` extracts the answer and ends the run; if the context-provided max-steps limit is hit without one, a forced final-answer LLM call over the full memory produces a think/answer JSON, recorded as an extra trajectory step. A `_process_response` hook lets subclasses intercept raw responses before parsing.
- **tool_policy.py — `AllToolsPolicy`**: The simplest policy — no filtering; every step exposes the entire tool catalog, serialized as a JSON schema list (with "any" types coerced to string and non-nullable inputs marked required). Optionally loads a skills registry of domain-knowledge text for prompt injection when explicitly enabled. `final_answer` is handled in action, not here.
- **prompt.yaml**: Defines `system_prompt` (memory's system message: DAG execution rules — parallelize across goals, one path per goal at a time, fallback only on failure, evidence-gated completion — plus the JSON output schema, tool strategy, and optional skills section); `planning.initial_plan` (planning's decomposition prompt with the goal/path output format); `summary.update_pre_messages`/`update_post_messages` (planning's periodic status-analysis prompts with per-goal Completed/In Progress/Blocked format and next parallel sub-paths); `step.pre_messages` (action's per-step prompt: tool list, task, example JSON, at most 5 and at least 1 tool call, no repeated calls); and `final_answer.pre_messages`/`post_messages` (action's forced-answer prompts requesting think/answer JSON).
