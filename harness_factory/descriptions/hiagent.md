### Harness: hiagent

**Overview**: HiAgent is a flat ReAct-style harness with no explicit planning; its distinguishing mechanism is hierarchical, value-based memory sampling. The full trajectory is stored internally, but each LLM call sees only the most informative prior steps, scored by boundary importance plus observation novelty, with pruned steps shown as `[Omitted]` placeholders. Control flow: a no-op planning step, then an Action/Observation loop where the LLM emits JSON tool calls (up to 5 per step) executed against the full tool catalog, ending when `final_answer` is called or a forced-answer call fires at the max-step limit. It suits long tool-using runs where context budget, not task decomposition, is the bottleneck.

**Component implementations**:
- **memory.py — `HierarchicalMemory`**: `MemoryStrategy` appends every StepRecord/PlanState/SummaryState to one ordered list; plan and summary items are never pruned. On context build, if steps exceed memory_size (default 15), it always keeps the first and last step and selects the top-(K-2) middle steps by a value function: an inverted-Gaussian boundary weight (w1=1.0) plus observation change rate 1−TF-IDF cosine similarity between consecutive observations (w2=1.0; word-overlap fallback), with a reward-delta term disabled (w3=0.0). Unselected steps become one-line `[Omitted]` placeholder messages in original order. If the sampled context exceeds 31768 tokens, K is decremented and rebuilt until it fits, falling back to system+task only.
- **planning.py — `NoPlanning`**: no real planning — `init_plan` returns a fixed "No explicit plan, proceed directly" PlanState, `should_replan` always returns false, and the directive is just the raw task echoed back. The plan record is stored once in memory at step 0 and never updated.
- **action.py — `ReActAction`**: `ActionStrategy` owns the loop: per step it rebuilds the memory view, appends a templated step prompt with tool schemas and the task, calls the LLM, and parses the reply with json_repair into a think string plus a tools list (dict or list forms both accepted). Each call is dispatched via the runtime's tool executor; tool errors become error-text observations, model-call failures are recorded as error steps and the loop continues. Loop ends when `final_answer` appears or step count exceeds ctx.max_steps, after which `_force_final_answer` makes one extra LLM call over the memory view asking for a JSON think/answer object, recorded as a trajectory step. Per-step token counts are logged, and a `_process_response` hook exists for subclasses.
- **tool_policy.py — `AllToolsPolicy`**: an all-tools policy — no filtering; every step exposes the entire catalog as pretty-printed JSON schemas (marking non-nullable inputs required, mapping "any" types to string). It optionally loads a skills registry when enabled and injects a formatted skills prompt; final_answer handling lives in action.py, not here.
- **prompt.yaml**: defines `system_prompt` (consumed at initialization; explains the JSON think/tools output format, warns about `[Omitted]` history, lists tools and optional skills, and sets rules like no duplicate calls and answer-language matching); `step.pre_messages` (per-step user prompt from action.py with tool list, task, schematic example, and the at-least-1/at-most-5 tool-call rule); `final_answer.pre_messages`/`post_messages` (forced-answer prompt demanding a JSON think/answer object); plus static `planning.initial_plan` and `summary.update_messages` placeholder strings for the no-op planner.
