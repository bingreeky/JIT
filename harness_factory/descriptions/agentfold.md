### Harness: agentfold

**Overview**: AgentFold is a hybrid harness combining Flash-Searcher-style DAG planning with AgentFold-style cooperative trajectory compression. A planner LLM call first decomposes the task into 1-5 parallel goals, each with 1-5 sequential fallback paths; a ReAct loop then executes JSON tool calls against this plan, re-summarizing progress every 8 steps. Its distinguishing mechanism is in-band history folding: the acting LLM may emit a top-level `compress` object naming a contiguous range of prior step ids plus replacement text, which memory folds into a single compressed entry. It suits long-horizon, multi-branch information-gathering tasks where parallel evidence collection and context economy both matter.

**Component implementations**:
- **memory.py — `AgentFoldMemory`**: Maintains a step list of start/end/content entries plus a raw-step archive and a monotonically increasing step id. Each executed step is stored as a formatted block containing the think text, tool name/arguments lines, and the full observations; plan and summary events become their own entries with content truncated to 1000 characters. Context rendering emits the system prompt, task messages, then each entry as an assistant message headed `[Step N]` for the newest step, `[Compressed Step N]` for older singles, or `[Compressed Step N to M]` for folded ranges, sorted by start id. There is no automatic eviction: `apply_compression` fires only when the action module forwards LLM-issued instructions, deleting all entries whose start falls inside the range and inserting one summarized entry.
- **planning.py — `FlashDAGPlanning`**: On initialization one LLM call (using the initial-plan prompt with tool schemas truncated to 2000 characters) produces a free-text DAG plan of 1-5 parallel goals, each with 1-5 fallback paths and per-path success criteria; the plan is recorded into memory as a step. Replanning triggers every 8 steps (configurable `summary_interval`): a summary LLM call over the current memory view analyzes per-goal/per-path status and recommends next parallel sub-paths, the result replaces the stored plan text and is appended to memory, and `get_directive` returns the current plan text.
- **action.py — `ReActFoldAction`**: The loop initializes memory context, selects tools, generates the initial plan, then iterates until a final answer or `ctx.max_steps`. Each step optionally runs the periodic plan update (which itself consumes a step number), rebuilds the memory view, renders the step prompt with the tool schema JSON via Jinja, and calls the LLM; the response is first intercepted for a top-level `compress` field (parsed with json_repair) and forwarded to memory, then parsed for `think` and a `tools` list executed sequentially, with per-tool exceptions converted into error observations. A `final_answer` tool call ends the loop; model-call failures are recorded as error steps and the loop continues. If max steps are hit, a forced-final-answer LLM call over the full memory produces a JSON think/answer response.
- **tool_policy.py — `AllToolsPolicy`**: An all-tools policy with no filtering — every step exposes the full catalog as a pretty-printed JSON schema string (any-typed params coerced to string, non-nullable params marked required). It can optionally load a skill registry whose formatted domain-knowledge text is injected into the system prompt. `final_answer` is handled purely by the action module, not the policy.
- **prompt.yaml**: Defines `system_prompt` (rendered into memory's system message): explains the goal/path execution model, parallel-across-goals but sequential-within-goal routing, the JSON output schema with optional `compress`, verification-before-completion rules, and a schematic worked example. `planning.initial_plan` instructs DAG decomposition with the structured goal/path/success format. `summary.update_pre_messages`/`update_post_messages` drive the periodic status analysis and next-parallel-sub-paths recommendation. `step.pre_messages` is the per-step action prompt consumed by the action loop, restating the tool list, task, detailed compression guidelines (contiguous ascending ids, never compress plan/summary steps or actively used evidence), and a 1-5 tool-calls-per-step constraint. `final_answer.pre/post_messages` back the forced-answer fallback.
