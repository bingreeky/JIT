### Harness: aggagent

**Overview**: AggAgent is a two-stage generate-then-adjudicate architecture that separates exploration from synthesis. Phase one runs K (default 4) independent ReAct rollout workers sequentially on the same task, each with its own isolated full-history memory and the full runtime tool catalog, splitting the global step budget evenly (minimum 5 steps each). Phase two converts each worker's trajectory into an OpenAI-style message list and hands them to a dedicated aggregator agent that never re-solves the task; instead it inspects trajectories via four meta-tools, verifies claims against raw tool observations, and emits one synthesized answer. Its distinguishing mechanism is evidence-over-confidence adjudication: the aggregator is instructed to trust tool outputs over agent reasoning and to distrust majority agreement. It fits short-answer tasks where redundant exploration plus cross-trajectory verification beats a single trajectory.

**Component implementations**:
- **memory.py — `AggMemory`**: Split-memory design with two classes and zero compression. The outer `MemoryStrategy` is only a coordinator: it stores the system prompt and task, renders context as just system + task messages, ignores plan/summary updates, and accepts the merged trajectory written back after the run for logging. Each rollout worker gets its own `FullHistoryMemory` that appends every step, plan, and summary verbatim and renders the entire uncompressed history (system, task, then all step messages) on every call. No eviction, summarization, or thresholds exist anywhere.
- **planning.py — `NoPlanning`**: Planning is deliberately disabled. The initial plan is the fixed string "No explicit plan. Proceed directly with the task.", replanning is never triggered, plan updates return a no-op summary, and the directive simply echoes the task. Control flow comes entirely from the rollouts plus the aggregation pass.
- **action.py — `AggAgentAction`**: Phase 1 runs each worker through a standard ReAct loop: render full history plus a step prompt embedding tool schemas, call the LLM, parse a JSON object with think and tools fields via json_repair, execute each tool, and stop when `final_answer` appears; on model errors the step is recorded and the loop continues, and hitting the per-worker step cap triggers a forced final-answer LLM call over the memory. Phase 3 runs the aggregator loop, capped at 100 iterations, dispatching only the first parsed tool call per turn among four in-file meta-tools: `get_solution` (last-step content per trajectory), `search_trajectory` (ROUGE-L-recall-ranked search, default 5 and max 10 matches, results truncated to 150 words, optional role filter), `get_segment` (contiguous window of at most 5 steps, 600-word truncation), and `finish` (validates that the solution contains non-empty explanation and answer XML sections). When approximate context (chars/4) exceeds 100,000 tokens, a final message is injected forcing a finish-only call; a turn with no valid tool call gets a format nudge, and if no valid finish ever arrives the result falls back to an empty answer with a failure reason. Meta-tool observations are truncated to 8,000 characters in the aggregator history and 4,000 in the step record; the final merged trajectory tags every step with its Rollout-i or Aggregator origin.
- **tool_policy.py — `AllToolsPolicy`**: An always-on policy that exposes the entire tool catalog at every step with no filtering, plus all loaded skills when skill support is enabled. It formats tool schemas as a JSON string (marking non-nullable inputs required, coercing "any" types to string) that the step prompt embeds. Only rollout workers use it; the aggregator ignores the catalog and uses its internal meta-tools, and `final_answer` is intercepted in the action loop rather than executed as a tool.
- **prompt.yaml**: Defines the worker-facing templates — `system_prompt` (JSON think/tools protocol, tool and skill listing, no-repeat-calls rules), `step.pre_messages` (per-step user prompt with tool JSON, task, and strict output format), `final_answer` pre/post messages for the forced-answer fallback, static `planning`/`summary` strings, and `rollout_worker.system_prompt_suffix` telling each worker its trajectory will be reviewed alongside others. The `aggregator` block supplies its `system_prompt` (required verify-before-finish procedure, tool-results-are-ground-truth and anti-majority-bias guidelines, self-contained explanation/answer format), `user_prompt` (task plus per-trajectory metadata: step counts, approximate tokens, tool-usage tallies), `step_prompt` (one meta-tool per turn with schemas), and `final_message` (the context-overflow force-finish instruction). All are consumed by action.py; memory and planning use none of them.
