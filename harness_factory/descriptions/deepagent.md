### Harness: deepagent

**Overview**: DeepAgent is a flat, plan-free tool-using harness built on a marker-based protocol instead of JSON ReAct. Each turn the LLM emits reasoning plus exactly one action — a tool call, a tool-catalog search, or a thought-fold marker — and the runtime executes it, appends the observation, and loops until a final answer or the step limit. Its distinguishing mechanism is "thought folding": on demand the trajectory is compressed by the LLM into three persistent memories (episodic, working, tool) and the active context resets, keeping long, noisy, or stuck runs tractable. It suits long-horizon tool tasks with large catalogs and verbose outputs.

**Component implementations**:
- **memory.py — `DeepAgentMemory`**: Keeps a full append-only item list (steps, plan/summary items) plus a parallel interaction log of tool calls with their observations. Context is rendered as system prompt (with a fold-memory block injected after any fold) + task + only the items after the last fold. `fold`, allowed at most 3 times per run, makes three sequential LLM calls producing JSON episodic memory (milestones, progress), working memory (immediate goal, challenges, next actions), and tool memory (per-tool success patterns, derived rules), then advances the fold boundary so prior items drop from context. Fold inputs truncate each observation to 2000 chars and each tool response in the tool-call history to 1000 chars.
- **planning.py — `NoPlanning`**: A deliberate no-op. The initial "plan" is a fixed sentence saying to proceed directly, replanning is never triggered, and the directive is just the task text; planning is implicit in the reasoning trace and the working memory produced by folds.
- **action.py — `DeepAgentAction`**: Each step builds context from memory, appends a per-step user prompt with the full tool schemas and task, and calls the LLM once. Output is truncated at the first complete marker block (to kill multi-turn simulations), then dispatched: tool_call is JSON-repaired and executed with exact-duplicate detection (repeat calls get a refusal message), the `final_answer` tool terminates the run, and observations longer than 5000 chars are LLM-summarized (input capped at 8000 chars, fallback truncation 3000); tool_search does keyword matching over the catalog (queries under 4 chars rejected, duplicates refused, no match returns all tools); fold_thought delegates to memory folding. Marker-free text becomes the final answer via boxed extraction or, if over 10 chars, verbatim; observations are stored raw, unwrapped, to prevent marker hallucination. If the run hits the max-step limit, a forced final-answer LLM call over memory produces the answer (parsed from JSON or boxed form).
- **tool_policy.py — `AllToolsPolicy`**: Exposes the entire tool catalog at every step with no filtering, pre-rendering all schemas as JSON (mapping "any" types to string and deriving required params from non-nullable inputs). Optionally loads a skill registry and supplies a domain-knowledge skills prompt for system-prompt injection. `final_answer` is handled in action, not filtered here.
- **prompt.yaml**: Defines `system_prompt` (used by memory's context build): explains the three markers, mandates exactly one action per turn, forbids self-generated result tags, shows a schematic multi-turn example, lists tools/skills via templating, and requires answer language to match the task. `step.pre_messages` (action, every step) restates the one-action rule with tool schemas and the task; `final_answer.pre/post_messages` (action, forced-answer path) ask for a JSON think/answer object; `planning.initial_plan` and `summary.update_messages` are static stubs for the no-op planner.
